# QS002 — Cartesian explosion

**Severity:** Error · **Detects:** a single-query result with two or more collection `Include`s where the rows returned are at least `CartesianExplosionFactor` (default 10) times the distinct root entities, and at least `CartesianMinimumRows` (default 50) rows.

## What it looks like

```csharp
var customers = await db.Customers
    .Include(c => c.Orders).ThenInclude(o => o.Lines)
    .Include(c => c.Addresses)
    .ToListAsync();
```

```
QS002 ERROR  Cartesian explosion: 1,200 rows for 40 Customer entities (Orders, Orders.Lines, Addresses) at BadEndpoints.cs:27 BadEndpoints.Map
  fix  Add .AsSplitQuery() to the Customer query so each collection loads with its own SELECT
```

## Why EF Core does this

With the default single-query mode, EF Core loads a root and all its included collections in **one** SQL statement by LEFT JOINing each collection
to the root. Two independent collections joined to the same root produce one row per *combination*: a customer with 15 order lines and 2 addresses
comes back as 30 rows, each repeating the customer columns and the columns of the other collection. EF Core de-duplicates in memory afterwards,
so the result is correct, but the database, the network and the materializer paid for rows that carried no new information. Adding a third collection
multiplies again.

QueryShape wraps the data reader and counts the rows actually read plus the distinct values of the first column (EF Core orders include results by root key,
projected first). Rows per root is the multiplication factor.

## Fix

- `AsSplitQuery()` on the query: one SELECT for the roots and one per collection, correlated by root key. Rows are transferred once each.
  Cost: one extra round trip per collection and no snapshot consistency between statements unless you use a transaction.
- Make it the default for a context: `optionsBuilder.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery)`.
- Or avoid loading whole graphs: project what the page needs (`Select(c => new { c.Name, Orders = c.Orders.Count })`).

## Notes

- Mild multiplication below the factor is reported by [QS006](QS006.md) as a candidate.
- The evidence says whether single-query loading was written at the call site (`splitting: AsSingleQuery (explicit)`) or inherited from the
  context default. An explicit `AsSingleQuery()` means someone already weighed rows against round trips, so the finding reports what that
  decision currently costs and the suggested patch says it reverses a deliberate choice. The last splitting call in the chain is the effective
  one, as in EF Core.
- Split queries and queries with a single collection include are never flagged.
