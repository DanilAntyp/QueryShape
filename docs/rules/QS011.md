# QS011 — Row limiting without OrderBy

**Severity:** Warning · **Detects:** `Skip`/`Take` (paging) or `First`/`Single` without an `OrderBy`, straight from EF Core's compile-time warnings
`RowLimitingOperationWithoutOrderByWarning` and `FirstWithoutOrderByAndFilterWarning`.

## What it looks like

```csharp
var orders = await db.Orders.Skip(page * size).Take(size).ToListAsync();
```

```
QS011 WARNING  Non-deterministic paging: Skip/Take without OrderBy on Order at OrdersController.cs:40 OrdersController.Page
  fix  Add .OrderBy(o => o.Id) (or an order that matches the UI) before the Skip/Take
```

## Why EF Core does this

A relational table has no inherent order. Without `ORDER BY` the database returns rows in whatever order the chosen plan produces, and that
order changes with indexes, statistics, parallelism and concurrent writes. EF Core translates `Skip`/`Take` faithfully to `OFFSET`/`LIMIT`
(or `TOP`) with no `ORDER BY`, so paging walks over a moving target: rows appear on two pages or on none, and the same request returns different
results minutes apart. `First()` without an order asks for "any one row". EF Core knows this and logs a warning when it compiles the query;
QueryShape subscribes to EF Core's diagnostic source and attaches that warning to the query it belongs to.

## Fix

- Add a total order before the row-limiting operator: a unique key, or a sort plus the key as tie-breaker
  (`.OrderBy(o => o.PlacedAt).ThenBy(o => o.Id)`).
- Order by an indexed column so the database does not sort the whole table to find one page.

## Notes

- This rule was added after the initial rule table (ADR-0008); it exists because the signal is already computed by EF Core and the bug is common.
- The warning fires once per compilation, so every execution of the query shape carries it.
