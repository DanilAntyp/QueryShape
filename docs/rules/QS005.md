# QS005 — Tracking on read-only query

**Severity:** Info · **Detects:** a query that returns entity instances with change tracking on, in a scope that never called `SaveChanges` for that entity type.

## What it looks like

```csharp
var products = await db.Products.Where(p => p.Price > 10).OrderBy(p => p.Sku).Take(10).ToListAsync();
return products.Select(p => new { p.Sku, p.Price });
```

```
QS005 INFO  Tracked read-only query: 10 Product entities loaded with change tracking but never modified at CatalogController.cs:31 CatalogController.List
  fix  Add .AsNoTracking() to the Product query; for read-mostly contexts set optionsBuilder.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking) ...
```

## Why EF Core does this

`DbContext` exists to detect changes and save them, so by default every entity a query materializes is **tracked**: EF Core creates a change-tracker
entry per instance and snapshots every property value so `SaveChanges` can later compute what changed. It also runs identity resolution, checking
each incoming row against already-tracked instances. On a request that only reads, all of that is overhead proportional to the rows loaded,
and the tracked entities keep the snapshots alive until the context is disposed.

## Fix

- `AsNoTracking()` on the query (or `AsNoTrackingWithIdentityResolution()` when the same entity appears repeatedly in the result and you want one instance).
- For a read-mostly context: `optionsBuilder.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking)` and opt back in with `.AsTracking()` where you save.
- Projections (`Select` to a DTO or anonymous type) are never tracked; prefer them for read models.

## Notes

- Info severity: this is a hint, never a failure by default. Snapshot tests record it as known debt.
- The rule only looks at the current scope: an entity loaded here and saved in another scope is reported. `IsTracking` is derived from the expression
  (`AsNoTracking`/`AsTracking`) and the context default; see ADR-0002 for the cross-context caveat.
- The evidence says whether tracking was asked for at the call site (`tracking: AsTracking (explicit)`) or inherited from the context default. An explicit
  `AsTracking()` on a path that never saves usually means something outside the scope relies on the tracked instances, so the finding says so.
- Keyless entity types (`HasNoKey`, views) are never tracked by EF Core and are never reported.
- A query that returned no rows (a lookup that found nothing) tracked nothing and is not reported.
- For collection includes, the title omits an entity count: joined database rows repeat the root entity and cannot be treated as a count of distinct roots. The evidence still records rows read.
- Saving any entity type the query loaded counts: the root or anything reached through `Include`/`ThenInclude` (`Customers.Include(c => c.Orders)` followed by
  an edited `Order` and `SaveChanges` is not reported).

## Interpretation boundary

This rule observes tracking and saves inside one scope. It does not establish that tracking is globally unnecessary: identity resolution or a later save outside the scope may require it. The wording intentionally says no save was observed. Compare returned DTOs and relevant persisted state before changing tracking; this diagnostic alone does not measure a latency improvement.
