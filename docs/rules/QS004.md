# QS004 — Unbounded result set

**Severity:** Warning · **Detects:** a LINQ query with no `Where` and no row-limiting operator (`Take`, `First`, `Single`, `Any`, `Count`, aggregates),
or any query that returned more than `UnboundedRowThreshold` rows (default 1000).

## What it looks like

```csharp
var orders = await db.Orders.Include(o => o.Lines).ToListAsync();   // every order, every line
```

```
QS004 WARNING  Unbounded query: loads every Order row (61 rows) at ReportService.cs:18 ReportService.All
  fix  Filter the Order query (.Where) or page it (.OrderBy(o => o.Id).Take(n))
```

## Why EF Core does this

A query without `Where` or `Take` translates to `SELECT … FROM Orders` with no `WHERE` and no `TOP`/`LIMIT`, so the database returns
the whole table. EF Core then materializes every row into an entity and, when tracking is on, snapshots every property for change detection.
The work is linear in the table size: fine in the test database, the slowest thing in the request once production has accumulated data,
and eventually an out-of-memory. An `Include` of a collection multiplies the rows transferred.

## Fix

- Filter: `.Where(o => o.CustomerId == customerId)`.
- Page: `.OrderBy(o => o.Id).Skip(page * size).Take(size)`.
- Aggregate in SQL: `.CountAsync()`, `.SumAsync(...)`, `.GroupBy(...)`.
- If every row really is needed (exports, batch jobs): stream with `AsAsyncEnumerable()` and add `AsNoTracking()` so memory stays flat.
- Small lookup tables are legitimately loaded whole: keep the diagnosis in the snapshot as known debt, or remove the rule for that test.

## Notes

- Raw SQL is judged by row count only (no expression tree). Threshold: `QueryShapeOptions.UnboundedRowThreshold`.
- Row counts are exact: QueryShape wraps the data reader and counts successful reads ([ADR-0004](../adr/0004-single-interceptor-options-extension-row-counting.md)).
